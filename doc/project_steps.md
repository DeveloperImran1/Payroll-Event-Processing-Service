# পেরোল ইভেন্ট প্রসেসিং সার্ভিস - প্রজেক্ট রোডম্যাপ (Project Roadmap)

যেহেতু আপনি NestJS এর পরিবর্তে **ExpressJS, Prisma, PostgreSQL, Redis** এবং **BullMQ** ব্যবহার করতে চাচ্ছেন, তাই এই টেকনোলজিগুলোর উপর ভিত্তি করে প্রজেক্টটি শুরু থেকে শেষ পর্যন্ত (প্ল্যানিং থেকে ডিপ্লয়মেন্ট) সম্পন্ন করার জন্য একটি সম্পূর্ণ ধাপভিত্তিক রোডম্যাপ নিচে দেওয়া হলো। 

আপনি চাইলে এই ধাপগুলো পর্যালোচনা করে কোনো পরিবর্তন থাকলে জানাতে পারেন। এরপর আমরা একে একে ধাপগুলো ধরে কাজ শুরু করতে পারবো।

---

## ফেজ ১: ইনিশিয়াল সেটআপ এবং কনফিগারেশন (Initial Setup & Configuration)

**Step 1: Project Initialization (প্রজেক্ট ইনিশিয়ালাইজেশন)**
- `npm init -y` দিয়ে প্রজেক্ট শুরু করা।
- TypeScript, `tsconfig.json` সেটআপ এবং প্রয়োজনীয় প্যাকেজগুলো ইন্সটল করা (express, dotenv, typescript, etc)।

**Step 2: Express Server Setup (এক্সপ্রেস সার্ভার সেটআপ)**
- সাধারণ Express সার্ভার তৈরি করা।
- Middleware সেটআপ করা (cors, express.json)।
- গ্লোবাল এরর হ্যান্ডলার (Global Error Handler) তৈরি করা।

**Step 3: Docker ও Environment Setup (ডকার ও এনভায়রনমেন্ট সেটআপ)**
- `docker-compose.yml` ফাইল তৈরি করা যেন PostgreSQL এবং Redis সার্ভার লোকালি রান করা যায়।
- `.env` ফাইল তৈরি করে প্রয়োজনীয় ডাটাবেস ও রিডিস কানেকশন ইউআরএল রাখা।

**Step 4: Prisma Setup (প্রিজমা সেটআপ)**
- প্রজেক্টে Prisma ইন্সটল করা (`npx prisma init`)।
- `.env` এর ডাটাবেস URL এর সাথে প্রিজমা কানেক্ট করা।

---

## ফেজ ২: ডাটাবেস ডিজাইন এবং মডেলিং (Database Design & Modeling)

**Step 5: Define Prisma Schema (ডাটাবেস মডেল তৈরি)**
- `schema.prisma` ফাইলে পেরোল ইভেন্টের জন্য টেবিল ডিজাইন করা। 
- ইভেন্টের ধরণ (BANK_ACCOUNT, ADDRESS, SALARY) এবং স্ট্যাটাস (PENDING, PROCESSING, SUCCESS, FAILED) এর জন্য Enum তৈরি করা।
- ইভেন্টের সম্পূর্ণ পে-লোড সেভ করার জন্য JSON ফিল্ড ব্যবহার করা।

**Step 6: Database Migrations (ডাটাবেস মাইগ্রেশন)**
- `npx prisma migrate dev` কমান্ড চালিয়ে ডাটাবেসে টেবিলগুলো তৈরি করা এবং স্কিমা সিঙ্ক করা।

---

## ফেজ ৩: API এবং ইনপুট ভ্যালিডেশন (API & Input Validation)

**Step 7: Health Check API (হেলথ চেক এন্ডপয়েন্ট)**
- `GET /health` এন্ডপয়েন্ট তৈরি করা যা নিশ্চিত করবে যে সার্ভার, ডাটাবেস এবং রিডিস ঠিকমতো কাজ করছে কিনা।

**Step 8: Event Submission API (ইভেন্ট সাবমিট এন্ডপয়েন্ট)**
- `POST /events` রাউট এবং কন্ট্রোলার তৈরি করা।

**Step 9: Input Validation with Zod/Joi (ইনপুট ভ্যালিডেশন)**
- ইউজারের পাঠানো রিকোয়েস্ট (employeeId, eventType, payload) সঠিক কিনা তা Zod বা Joi দিয়ে ভ্যালিডেট করা (ভিন্ন ভিন্ন ইভেন্টের জন্য ভিন্ন ভিন্ন ভ্যালিডেশন স্কিমা)। 

**Step 10: Database Persistence (ডাটাবেসে সেভ করা)**
- ভ্যালিডেশন পাস হলে ডাটাবেসে ইভেন্টটিকে `PENDING` স্ট্যাটাসে সেভ করা।

---

## ফেজ ৪: মেসেজ কিউ সেটআপ (Message Queue Setup)

**Step 11: Redis Connection Setup (রিডিস কানেকশন তৈরি)**
- Ioredis বা Redis ক্লায়েন্ট দিয়ে অ্যাপের সাথে রিডিসের কানেকশন তৈরি করা।

**Step 12: BullMQ Queue Initialization (BullMQ কিউ তৈরি করা)**
- `payroll-events-queue` নামে একটি BullMQ Queue তৈরি করা।

**Step 13: Enqueue Jobs (জব কিউতে পাঠানো)**
- `POST /events` API তে ডাটাবেসে ইভেন্ট সেভ হওয়ার পরপরই ইভেন্টের ID সহ সেটি কিউতে (Queue) পুশ করে দেওয়া এবং সাথে সাথে ইউজারকে API রেসপন্স দিয়ে দেওয়া।

---

## ফেজ ৫: ওয়ার্কার এবং অ্যাসিনক্রোনাস প্রসেসিং (Worker & Asynchronous Processing)

**Step 14: BullMQ Worker Setup (ওয়ার্কার তৈরি)**
- কিউ থেকে ইভেন্টগুলো ধরে প্রসেস করার জন্য একটি আলাদা Worker ফাইল/ক্লাস তৈরি করা।

**Step 15: Event Status Update (স্ট্যাটাস আপডেট)**
- ওয়ার্কার কাজ শুরু করলেই ডাটাবেসে ইভেন্টের স্ট্যাটাস `PENDING` থেকে `PROCESSING` এ আপডেট করে দেওয়া।

**Step 16: Processing Simulation (প্রসেসিং সিমুলেশন)**
- আসল পেরোল API এর বদলে `setTimeout` দিয়ে কয়েক সেকেন্ডের একটি সিমুলেটেড প্রসেস তৈরি করা, যা র‍্যান্ডমলি মাঝে মাঝে ফেইল করবে।

**Step 17: Idempotency Check (ডুপ্লিকেট রিকোয়েস্ট থামানো)**
- একই ইভেন্ট যেন ডাটাবেসে দুইবার অপারেশন না করতে পারে তার জন্য ওয়ার্কারের শুরুতে একটি Idempotency চেক রাখা।

**Step 18: Handle Failures and Retries (ফেইলিউর ও রিট্রাই সামলানো)**
- প্রসেস ফেইল হলে BullMQ এর সাহায্যে নির্দিষ্ট সময় পর পর অটোমেটিক রিট্রাই (Retry) করানো।
- কিছু নির্দিষ্ট এররের ক্ষেত্রে রিট্রাই না করে সরাসরি ডাটাবেসে `FAILED` স্ট্যাটাস দিয়ে দেওয়া।

**Step 19: Final Status Save (চূড়ান্ত ফলাফল সেভ)**
- প্রসেসিং সফল হলে ডাটাবেসে `SUCCESS` এবং ব্যর্থ হলে `FAILED` ও এরর মেসেজ সেভ করা।

**Step 20: Event Status API (স্ট্যাটাস দেখার API)**
- `GET /events/:id` API তৈরি করা যেন ইউজার যেকোনো সময় তার ইভেন্টের বর্তমান স্ট্যাটাস জানতে পারে।

---

## ফেজ ৬: ফ্রন্টএন্ড ডেভেলপমেন্ট (Frontend Development)

**Step 21: Minimal Frontend Setup (ফ্রন্টএন্ড তৈরি)**
- ReactJS বা সাধারণ HTML/Vanilla JS দিয়ে একটি সিম্পল ফ্রন্টএন্ড প্রজেক্ট তৈরি করা।

**Step 22: Event Submission Form (সাবমিশন ফর্ম)**
- তিন ধরণের ইভেন্ট সাবমিট করার জন্য ফ্রন্টএন্ডে ফর্ম তৈরি এবং ব্যাকএন্ড API তে ডাটা পাঠানো।

**Step 23: Status Dashboard (স্ট্যাটাস ড্যাশবোর্ড)**
- সাবমিট করা ইভেন্টগুলোর লিস্ট এবং তাদের বর্তমান স্ট্যাটাস (রিয়েল-টাইম বা রিফ্রেশ করে) দেখার ব্যবস্থা করা।

---

## ফেজ ৭: টেস্টিং এবং লগিং (Testing & Logging)

**Step 24: Logging Setup (লগিং সেটআপ)**
- প্রসেস শুরু, শেষ, এবং ফেইল হওয়ার গুরুত্বপূর্ণ ইভেন্টগুলো টার্মিনালে সুন্দরভাবে দেখানোর জন্য `Winston` বা `Morgan` সেটআপ করা।

**Step 25: Setup Testing Framework (টেস্টিং ফ্রেমওয়ার্ক)**
- প্রজেক্টে Jest এবং Supertest ইন্সটল করা।

**Step 26: Write Automated Tests (অটোমেটেড টেস্ট লেখা)**
- ইভেন্ট সাবমিশন, ভ্যালিডেশন, ফেইলিউর হ্যান্ডেলিং এবং অন্যান্য লজিকের জন্য ইউনিট ও ইন্টিগ্রেশন টেস্ট লেখা।

---

## ফেজ ৮: CI/CD, ডকুমেন্টেশন এবং ডিপ্লয়মেন্ট (CI/CD, Docs & Deployment)

**Step 27: API Documentation (API ডকুমেন্টেশন)**
- Swagger বা Postman কালেকশন জেনারেট করে প্রজেক্টে যুক্ত করা।

**Step 28: GitHub Actions CI Pipeline (সিআই পাইপলাইন তৈরি)**
- `.github/workflows/ci.yml` তৈরি করা যেন GitHub এ পুশ করলেই অটোমেটিক টেস্ট ও বিল্ড চেক হয়।

**Step 29: Containerization (কন্টেইনারাইজেশন)**
- প্রজেক্টের API এবং Worker যেন আলাদা প্রসেস হিসেবে চলতে পারে তার জন্য `Dockerfile` তৈরি করা এবং `docker-compose.yml` আপডেট করা।

**Step 30: README and Final Review (রিডমি ও রিভিউ)**
- প্রজেক্ট কীভাবে রান করতে হবে, আর্কিটেকচার এবং আপনার নেওয়া সিদ্ধান্তগুলো বিস্তারিতভাবে README.md ফাইলে গুছিয়ে লেখা এবং একটি ডায়াগ্রাম যুক্ত করা।
