# পেরোল ইভেন্ট প্রসেসিং সার্ভিস - জব টাস্ক বিশ্লেষণ (Payroll Event Processing Service - Job Task Analysis)

এই ডকুমেন্টে আপনার ব্যাকএন্ড ইঞ্জিনিয়ারিং জব টাস্কের প্রতিটি অংশ বিস্তারিতভাবে বাংলায় ব্যাখ্যা করা হলো।

## উদ্দেশ্য (Purpose)
আপনাকে একটি ছোট কিন্তু প্রোডাকশন-রেডি (production-oriented) ব্যাকএন্ড সার্ভিস তৈরি করতে হবে। এর মূল উদ্দেশ্য হলো Node.js ইকোসিস্টেম ব্যবহার করে আপনি কতটা ভালোভাবে রিলায়েবল এবং অ্যাসিনক্রোনাস (asynchronous) ওয়ার্কফ্লো ডিজাইন করতে পারেন তা যাচাই করা। তারা আপনার কোডের পরিমাণের চেয়ে আপনার ইঞ্জিনিয়ারিং সিদ্ধান্ত নেওয়ার ক্ষমতাকে বেশি গুরুত্ব দেবে।

## সময়কাল (Time Expectation)
টাস্কটি শেষ করার জন্য ২-৩ দিন সময় দেওয়া হয়েছে। অপ্রয়োজনীয় ফিচারে ভরা বড় অ্যাপ্লিকেশনের চেয়ে, ছোট, নির্ভুল এবং ভালোভাবে টেস্ট করা অ্যাপ্লিকেশন তারা বেশি পছন্দ করবে।

## প্রযুক্তিগত প্রয়োজনীয়তা (Technology Requirements)
আপনাকে নিচের প্রযুক্তিগুলো ব্যবহার করতে হবে:
- Node.js
- TypeScript
- NestJS (ফ্রেমওয়ার্ক)
- PostgreSQL (ডাটাবেস)
- Redis (ক্যাশিং/মেসেজ ব্রোকার)
- BullMQ (অ্যাসিনক্রোনাস জব বা কিউ প্রসেসিংয়ের জন্য)
- Docker / Docker Compose (লোকাল ডেভেলপমেন্টের জন্য)
- Git ও GitHub Actions (ভার্সন কন্ট্রোল এবং CI/CD)

**অতিরিক্ত:** ডাটাবেস এক্সেস করার জন্য আপনি Prisma, Drizzle, বা TypeORM ব্যবহার করতে পারেন। অ্যাপ্লিকেশনটি দেখানোর জন্য একটি সাধারণ (minimal) ফ্রন্টএন্ড তৈরি করতে হবে (যেকোনো ফ্রেমওয়ার্ক বা ল্যাঙ্গুয়েজ ব্যবহার করতে পারেন)।

## সাধারণ ফ্রন্টএন্ড (Minimal Frontend Demonstration)
আপনাকে একটি খুব সাধারণ ফ্রন্টএন্ড বানাতে হবে যেন আপনার ব্যাকএন্ড সিস্টেমটি কাজ করছে তা ব্রাউজার থেকে টেস্ট করা যায়। খুব সুন্দর ডিজাইনের প্রয়োজন নেই। 
এটিতে নিচের সুবিধাগুলো থাকতে হবে:
১. পেরোল ইভেন্ট সাবমিট করার ফর্ম।
২. সাবমিট করা ইভেন্টগুলোর লিস্ট দেখা।
৩. একটি নির্দিষ্ট ইভেন্টের বিস্তারিত এবং বর্তমান স্ট্যাটাস দেখা।
৪. ইভেন্ট প্রসেস হওয়ার পর সফল বা ব্যর্থ হওয়ার কারণ দেখা।
৫. প্রসেসিংয়ের স্ট্যাটাস পরিবর্তন হলে তা যেন বোঝা যায়।

## প্রজেক্টের দৃশ্যপট (Project Scenario)
আপনাকে এমন একটি ব্যাকএন্ড সার্ভিস বানাতে হবে যা কর্মচারীদের পেরোল (বেতন/ভাতা) সম্পর্কিত ইভেন্ট গ্রহণ এবং প্রসেস করবে। তিন ধরণের ইভেন্ট সাপোর্ট করতে হবে: 
১. ব্যাংক একাউন্ট পরিবর্তন (Bank account changes)
২. ঠিকানা পরিবর্তন (Address changes)
৩. বেতন পরিবর্তন (Salary changes)

**গুরুত্বপূর্ণ:** প্রসেসিংয়ের সময় বাইরের কোনো সিস্টেম (Third-party API) ধীরগতির বা ফেইল হতে পারে বলে ধরে নিতে হবে। তাই আপনার সিস্টেমকে রিকোয়েস্ট গ্রহণ করা এবং তা ব্যাকগ্রাউন্ডে প্রসেস করা—এই দুই ভাগ আলাদা করতে হবে। ফেইল হলে পুনরায় চেষ্টা করা (retries), ডুপ্লিকেট রিকোয়েস্ট সামলানো এবং একাধিক ওয়ার্কার একসাথে কাজ করার বিষয়গুলো হ্যান্ডেল করতে হবে।

## ইভেন্ট টাইপসমূহ (Supported Event Types)
১. **BANK_ACCOUNT_CHANGE**: ফিল্ডস - `employeeId`, `effectiveDate`, `iban`
২. **ADDRESS_CHANGE**: ফিল্ডস - `employeeId`, `effectiveDate`, `street`, `city`, `postalCode`, `country`
৩. **SALARY_CHANGE**: ফিল্ডস - `employeeId`, `effectiveDate`, `newSalary`, `currency`

## ফাংশনাল রিকোয়ারমেন্টস (Functional Requirements)

১. **Event Submission (ইভেন্ট সাবমিশন):** 
একটি API এন্ডপয়েন্ট বানাতে হবে (যেমন: `POST /events`)। এটি রিকোয়েস্ট ভ্যালিডেট করবে, ডাটাবেসে সেভ করবে এবং ব্যাকগ্রাউন্ডে প্রসেস করার জন্য কিউতে (Queue) পাঠাবে। সাথে সাথে ইউজারকে রেসপন্স দিয়ে দিতে হবে, প্রসেস শেষ হওয়া পর্যন্ত ইউজারের রিকোয়েস্ট আটকে রাখা যাবে না।

২. **Event Status (ইভেন্ট স্ট্যাটাস):** 
একটি API এন্ডপয়েন্ট বানাতে হবে (যেমন: `GET /events/:id`)। এটি দিয়ে জানা যাবে ইভেন্টটি এখন কোন অবস্থায় আছে (পেন্ডিং, প্রসেসিং, সফল নাকি ব্যর্থ)।

৩. **Asynchronous Processing (অ্যাসিনক্রোনাস প্রসেসিং):** 
Redis এবং BullMQ ব্যবহার করে ইভেন্টগুলো ব্যাকগ্রাউন্ডে প্রসেস করতে হবে। এখানে আসল কোনো পেরোল প্রোভাইডারের API কল করতে হবে না, বরং `setTimeout` বা এরকম কিছু দিয়ে প্রসেসিং সিমুলেট করতে হবে। মাঝে মাঝে ইচ্ছা করে ফেইল করাতে হবে যাতে ফেইলিউর সিনারিও টেস্ট করা যায়।

৪. **Temporary and Permanent Failures (অস্থায়ী ও স্থায়ী ব্যর্থতা):** 
ধরে নিন বাইরের সিস্টেমটি সব সময় এভেইলেবল থাকে না। 
- টেম্পোরারি ফেইল হলে ইভেন্টটি একেবারে ফেইলড বলা যাবে না, কিছুক্ষণ পর আবার ট্রাই (retry) করতে হবে।
- কিছু এরর আছে যা কখনোই সফল হবে না (যেমন ভুল ডাটা), সেগুলোকে পার্মানেন্ট ফেইলড হিসেবে মার্ক করতে হবে।

৫. **Duplicate Requests (ডুপ্লিকেট রিকোয়েস্ট):** 
নেটওয়ার্ক সমস্যার কারণে ক্লায়েন্ট হয়তো একই রিকোয়েস্ট দুইবার পাঠাতে পারে। আপনার সিস্টেমকে বুঝতে হবে যে এটি একই রিকোয়েস্ট এবং একই পরিবর্তন যেন ডাটাবেসে দুইবার না হয় (Idempotency)।

৬. **Multiple Workers and Concurrency (একাধিক ওয়ার্কার ও কনকারেন্সি):** 
প্রোডাকশনে একাধিক ওয়ার্কার চলতে পারে। আপনার ডিজাইন এমন হতে হবে যেন একাধিক ওয়ার্কার চললেও একই ইভেন্ট দুইবার প্রসেস না হয়ে যায়।

৭. **Worker Failure and Recovery (ওয়ার্কার ফেইলিউর ও রিকভারি):** 
কোনো ইভেন্ট প্রসেস করার মাঝপথে ওয়ার্কার ক্র্যাশ করতে পারে। সিস্টেম আবার চালু হলে ঐ ইভেন্টটি যেন আটকে না থাকে, বরং সঠিকভাবে রিকভার করে কাজ শেষ করতে পারে।

৮. **Processing Consistency (প্রসেসিং কন্সিস্টেন্সি):** 
ধরে নিন: ওয়ার্কার ইভেন্ট রিসিভ করলো -> পেরোল অপারেশন সফল হলো -> ডাটাবেসে সেভ হলো -> কিন্তু প্রসেসটি 'finished' মার্ক হওয়ার আগেই ক্র্যাশ করলো -> পরে ইভেন্টটি আবার প্রসেস হতে আসলো।
আপনার কোড এমনভাবে লিখতে হবে যেন এই পরিস্থিতিতে একই পেরোল দুইবার অ্যাপ্লাই না হয় এবং ডাটা করাপ্ট না হয়। (Idempotency Key ব্যবহার করতে পারেন)

৯. **Event Ordering (ইভেন্ট ক্রমানুসারে সাজানো):** 
একই কর্মচারীর (employeeId) ইভেন্টগুলো যে সিরিয়ালে সিস্টেমে এসেছে, ঠিক সেই সিরিয়ালেই প্রসেস হতে হবে। তবে ভিন্ন ভিন্ন কর্মচারীর ইভেন্ট একসাথে প্রসেস হতে পারবে।

১০. **Extensibility (সম্প্রসারণযোগ্যতা):** 
কোডের আর্কিটেকচার এমনভাবে ডিজাইন করবেন যেন ভবিষ্যতে নতুন ইভেন্ট টাইপ (যেমন: EMPLOYEE_TERMINATION) যোগ করতে পুরো সিস্টেম নতুন করে লিখতে না হয়।

১১. **Validation (ভ্যালিডেশন):** 
প্রতিটি ইভেন্টের জন্য সঠিক ডাটা আসছে কিনা তা চেক করতে হবে। ভুল ডাটা আসলে API থেকে এরর রেসপন্স দিতে হবে। (NestJS এর Class Validator ব্যবহার করতে পারেন)

১২. **Event History and Audit Information (ইভেন্টের ইতিহাস):** 
একটি ইভেন্ট কখন সাবমিট হলো, কখন প্রসেস শুরু হলো, সফল হলো নাকি ব্যর্থ হলো- এই পুরো লাইফসাইকেল ডাটাবেসে ট্র্যাক করে রাখতে হবে। 

## টেস্টিং (Testing Requirements)
অটোমেটেড টেস্টিং (Automated testing) বাধ্যতামূলক। আপনাকে নিশ্চিত করতে হবে যে:
- সঠিক ইভেন্ট সাবমিট হচ্ছে, ভুল ইভেন্ট রিজেক্ট হচ্ছে।
- টেম্পোরারি ফেইলগুলো হ্যান্ডেল করা হচ্ছে এবং পার্মানেন্ট ফেইলগুলো সঠিকভাবে দেখানো হচ্ছে।
- ডুপ্লিকেট রিকোয়েস্ট দুইবার অপারেশন করছে না।

## ডকার ও লোকাল ডেভেলপমেন্ট (Docker and Local Development)
প্রজেক্টটি রান করা যেন খুব সহজ হয়। `docker compose up` কমান্ড দিলেই যেন NestJS API, ওয়ার্কার, PostgreSQL, Redis এবং ফ্রন্টএন্ড সব একসাথে চালু হয়ে যায়।

## CI Pipeline (সিআই পাইপলাইন)
GitHub Actions ব্যবহার করে একটি CI পাইপলাইন তৈরি করতে হবে যা কোড পুশ করলে অটোমেটিকভাবে টেস্ট রান করবে।

## Error Handling and Logging (এরর হ্যান্ডেলিং এবং লগিং)
অপ্রত্যাশিত এরর হ্যান্ডেল করতে হবে। ইভেন্ট প্রসেসিং শুরু, সফল, ব্যর্থ বা রিট্রাই করার সময় উপযুক্ত লগ জেনারেট করতে হবে যেন সহজে ডিবাগ করা যায়।

## Health Check (হেলথ চেক)
একটি `GET /health` এন্ডপয়েন্ট বানাতে হবে যা চেক করবে আপনার সার্ভিস ঠিকভাবে কাজ করছে কিনা।

## ডকুমেন্টেশন (API Documentation & README)
- **API Documentation:** Swagger বা Postman কালেকশন দিতে হবে।
- **README:** প্রজেক্ট সেটআপ, ডাটাবেস মাইগ্রেশন, টেস্টিং, আর্কিটেকচার এবং আপনার নেওয়া বিভিন্ন ইঞ্জিনিয়ারিং সিদ্ধান্তগুলোর কারণ ব্যাখ্যা করে একটি সুন্দর README লিখতে হবে। একটি ছোট আর্কিটেকচার ডায়াগ্রামও দিতে হবে।

## যা করার দরকার নেই (Scope - What Is Not Required)
- অনেক সুন্দর বা অ্যাডভান্স ফ্রন্টএন্ড।
- ইউজার রেজিস্ট্রেশন/লগিন বা অথেন্টিকেশন।
- অ্যাডমিন ড্যাশবোর্ড বা সম্পূর্ণ HR সিস্টেম।
- রিয়েল পেরোল প্রোভাইডারের সাথে ইন্টিগ্রেশন।
- Kubernetes বা জটিল ক্লাউড ইনফ্রাস্ট্রাকচার। 
(শুধুমাত্র মূল ব্যাকএন্ড প্রবলেমটির দিকে ফোকাস করুন)।

## এআই ব্যবহার (AI Usage)
আপনি ChatGPT, GitHub Copilot বা অন্যান্য AI টুল ব্যবহার করতে পারবেন। তবে আপনাকে প্রতিটি কোডের লজিক বুঝতে হবে, কারণ পরবর্তীতে টেকনিক্যাল ইন্টারভিউতে তারা আপনাকে কোড এবং আর্কিটেকচার সম্পর্কে বিভিন্ন প্রশ্ন করবে।

## সাবমিশন চেকলিস্ট (Submission Checklist)
- GitHub রিপোজিটরির লিংক।
- সিম্পল ফ্রন্টএন্ড ডেমো।
- সেটআপ ইন্সট্রাকশন সহ README।
- ডকার সেটআপ।
- ডাটাবেস স্কিমা এবং মাইগ্রেশন।
- অটোমেটেড টেস্টস।
- GitHub Actions ওয়ার্কফ্লো।
- API ডকুমেন্টেশন।
- আর্কিটেকচার এবং ডিজাইনের ব্যাখ্যা।

## টেকনিক্যাল রিভিউ (Technical Review After Submission)
সাবমিট করার পর ইন্টারভিউতে আপনাকে যা যা ব্যাখ্যা করতে হতে পারে:
- একটি ইভেন্টের সম্পূর্ণ লাইফসাইকেল।
- সিস্টেমের আর্কিটেকচার ও ডাটাবেস ডিজাইন।
- অ্যাসিনক্রোনাস প্রসেসিং কীভাবে কাজ করে।
- ফেইল এবং রিকভারি কিভাবে হয়।
- ডুপ্লিকেট প্রসেসিং কিভাবে ঠেকানো হয়েছে।
- টেস্টিং স্ট্র্যাটেজি এবং CI পাইপলাইন।
- ছোটখাটো কোড পরিবর্তন করে দেখাতে বলতে পারে।
